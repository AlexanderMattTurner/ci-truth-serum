- `startup-failure-scan` (apply-side console script, not a pre-commit lint and not in any tier aggregate): names the workflows whose runs failed before any job started. GitHub creates a run for a workflow file it cannot load; the run completes, carries a failure, and holds zero jobs. That shape reaches nobody, because every reporting route needs a job: a notifier that watches through `on.workflow_run` has no job to name, an `if: always()` reporter never runs, and the required check it would have posted waits at `Expected — Waiting` instead of turning red. No static lint can find it either, since the file the Actions loader rejects is the file PyYAML parsed happily. The scan spends one run listing per workflow, so its cost tracks the number of workflows and not the number of runs, and it asks for `status=completed` and classifies each conclusion itself — a `status=failure` listing never returns a `startup_failure` run, so the obvious implementation reports every repo healthy. It excludes `cancelled` and `skipped`, which hold zero jobs in normal operation. Exits non-zero on a finding, `--report-only` to publish without failing, `--format markdown` for a tracking-issue table, and it reports a partly read window as a floor rather than as a clean result. This repo runs it every Monday from `.github/workflows/startup-failure-scan.yaml`, which consumers can copy; the job needs only the `actions: read` permission. That workflow is in the notifier's watched list, and `tests/test_startup_failure_scan_wiring.py` pins the wiring, so this script cannot repeat the `release-canary` failure of shipping as an entry point that nothing invokes.
